# Клієнт-серверна модель довіри та мережева авторизація SafeVault (ЛР №10–11)

## 1. Розподіл функцій і даних (Межа довіри)
Клієнтське середовище вважається **недовіреним** (Zero-Trust), оскільки користувач контролює клієнтський застосунок, може аналізувати трафік і формувати довільні HTTP-запити. Критичні операції та перевірки прав виконуються виключно на стороні сервера:

| Компонент | Зона довіри | Функції та дані |
| :--- | :--- | :--- |
| **Клієнт (UI / HTTP Client)** | Untrusted Zone | Відображення інтерфейсу користувача, первинна валідація форм, обов'язкова перевірка TLS-сертифіката сервера (HTTPS), зберігання `access_token` в оперативній пам'яті та передавання заголовка `Authorization: Bearer <token>`. |
| **Сервер (SafeVault API)** | Trusted Zone | Зберігання криптографічних ключів (`SAFEVAULT_MASTER_KEY`, ключ підпису JWT, закритий ключ ліцензій), автентифікація суб'єктів, шифрування `AES-256-GCM`, контроль цілісності `HMAC-SHA256` та повторна перевірка прав доступу для кожного запиту. |

## 2. Мережева автентифікація та підтримання стану
* **Схема автентифікації:** для клієнтських застосунків за участю користувача використовується **OAuth 2.0 Authorization Code + PKCE**, для міжсервісної взаємодії — **Client Credentials** (застарілі схеми *Implicit* та *Resource Owner Password Credentials* заборонені).
* **Access Token:** короткоживучий структурований **JWT** (строк дії — 15 хвилин), підписаний на сервері за алгоритмом `HMAC-SHA256` (`HS256`). Містить твердження `sub` (ідентифікатор користувача), `role` (`USER` або `ADMIN`), `iat`, `exp` та унікальний `jti`.
* **Refresh Token:** непрозорий криптографічно випадковий токен для оновлення `access_token`, який передається у захищеному `HttpOnly; Secure; SameSite=Strict` cookie та має **одноразову ротацію** (повторне використання вже заміненого токена блокує всі сесії користувача як ознаку компрометації).

## 3. Серверна авторизація та обробка запитів
* **Ігнорування клієнтських атрибутів:** сервер відкидає будь-які заголовки чи параметри запиту на кшталт `X-Role` або `ownerId`. Ідентифікатор користувача та його роль витягуються виключно з верифікованого JWT після перевірки криптографічного підпису й строку дії.
* **Модель доступу (RBAC + ABAC):** перед виконанням захищеної операції сервер перевіряє роль користувача (`RBAC`) та належність ресурсу власнику (`ABAC / Ownership`).
* **Коди відповідей REST API:** `200 OK` / `204 No Content` (успіх), `401 Unauthorized` (відсутній, прострочений або підроблений токен), `403 Forbidden` (недостатньо прав або спроба доступу до чужого ресурсу).
